# 2026-11-24 修订记录

## 用户反馈与已确认事实

用户在普通终端执行设备脚本，两个APK均显示安装Success；游戏能正常启动，基本功能可用。首轮测试最后报 `Resume failed`。用户同时指出UI和设计与原版不同。

## 原版局内视觉恢复

前一版迁移中额外设计的深色HUD卡片、蓝色文字和结束排版不是原版的一部分，本次取消这些改动，直接对照原版 `AbstractGame` 的绘制代码迁移。

| 元素 | 原版与本次修订 |
| --- | --- |
| HUD | 红色22号粗体；SCORE/LIFE/DIFFICULTY分别位于(10,25)、(10,50)、(10,75)；不增加卡片背景 |
| 结束遮罩 | 黑色，透明度0.6 |
| GAME OVER | 60号红字，基线430，保留原版偏移3像素的暗红阴影 |
| 最终得分 | 24号金字，基线380，位于标题上方 |
| 提示文字 | 20号浅灰字，基线490；ESC返回菜单改为与本次入口一致的“点击画面重新开始” |
| 冰冻效果 | 恢复浅蓝半透明底色、双层圆角边框、十字/对角裂纹及亮点 |

本次仍按实验二默认直接进入简单模式，姓名输入、难度选择、排行榜页未迁移；移动端操作不能直接照搬桌面的ESC键。这些差异已明确记录，而非声称整个桌面UI原样移植。

## 设备恢复测试修订

首轮回执不足以确认游戏恢复本身损坏。原测试有两处需要修正：

1. 在目标应用已经退到后台后，让目标应用自己发起 `startActivity`。系统可能限制这种后台启动。本次改用Instrumentation的UiAutomation执行shell启动，模拟外部启动入口；启动返回文本写入测试报告。
2. 旧测试用逻辑tick是否增加判断恢复成功，但GAME_OVER后tick本来就应停止；同时旧引用在Activity被系统重建后也可能失效。本次监听实际恢复的Activity，以提交画布帧是否增加验证绘制循环，并继续检查后台停止和单线程约束。

这两项属于测试设计缺陷与误判风险。修订版测试尚未在设备执行，不能据此宣称首轮失败的确切原因或恢复已通过。失败时另外保存 `app/build/device-lifecycle-logcat.txt`。

## JBR原生访问警告

此前 `System::loadLibrary` 警告来自本机JBR与SDK签名工具的原生库调用，日志中的Verifies说明签名成功。本次只对直接调用的SDK `apksigner.jar` 加 `--enable-native-access=ALL-UNNAMED`，没有改变用户全局Java设置。重新构建的两份签名日志已不再出现该警告。
